# Phase 3 — Full UI Redesign

**Depends on:** P1 (schema is final), P2 (component vocabulary exists)
**Blocks:** nothing — later phases add screens using this system

## Goal

Convert every screen to Tailwind, remove Bootstrap and crispy-forms entirely, and build
the subscriber screens against the P1 schema.

## Why it sits here

Pulled ahead of all MikroTik work so visible progress lands early. Kept behind P1 because
the subscriber screens render fields that P1 reshapes — `ip` splits into typed connection
fields, `speed` splits into up/down. Converting before P1 means building those screens twice.

## The one rule

**Convert the whole app.** A half-Tailwind, half-Bootstrap codebase means maintaining two
design systems through every subsequent phase, and every P4–P7 screen has to pick a side.
If this phase gets cut short, cut scope from features, not from coverage.

---

## Conversion order

Dependency-ordered so shared layout lands first and the highest-traffic screens get the
most iteration time.

### 3.1 Shell

- [ ] `templates/base.html` — sidebar nav, top bar, theme toggle, message toasts
- [ ] Navigation reflects the four roles from P0: a collector sees payments and
      subscribers, not routers or packages
- [ ] Mobile: sidebar collapses to a drawer
- [ ] Django messages framework styled as toasts

### 3.2 Dashboard

The screen that decides whether anyone needs to act today. Summary before detail.

- [ ] KPI row: online now, in grace, suspended, routers down, sync drift
- [ ] KPI values colored **only when they are a problem** — a zero in "routers down" is
      not red, it is neutral
- [ ] "Routers down" names the specific router inline, removing a click
- [ ] Router health table (populated in P4 — until then, static rows from the DB)
- [ ] Recent service events feed
- [ ] HTMX polling on the whole panel, ~15s

Until P4 lands there is no live session data. Build the layout with DB-backed counts and
leave the live fields wired but empty — do not fake numbers.

### 3.3 Subscribers

The heaviest screen set, and the one the business runs on.

**List view**
- [ ] Filter by state, package, router, POP, expiry window
- [ ] Search across name, account no, phone, PPPoE username, IP
- [ ] State pill and sync pill per row
- [ ] Expiry column showing relative time (`in 2 days`, `12 days ago`) with the absolute
      date on hover
- [ ] Bulk selection, with typed confirmation for any bulk action
- [ ] Keep `django-filter` — it already backs these views and works fine; only the
      rendering changes

**Detail view**
- [ ] Header: name, state pill, account no, router, expiry
- [ ] Action buttons gated by permission — a collector sees "Record payment" but not
      "Suspend"
- [ ] Connection panel: type, username/IP, session IP, rate limit, uptime, sync state
- [ ] Billing panel: package, price, balance due, next invoice
- [ ] **Service history timeline** — merges billing events, state transitions, and router
      operations into one record, distinguishing automatic actions from named people.
      This is the screen you open when a customer disputes a disconnection.
- [ ] Timeline reads from `ServiceEvent` (P0)

**Create / edit form**
- [ ] Connection-type toggle swapping PPPoE and static-IP field groups (Alpine)
- [ ] PPPoE password generated by default, revealable, copyable
- [ ] Router and package selects showing enough context to pick correctly
- [ ] Validation surfaces the P1 check constraints as readable field errors, not a 500

### 3.4 Billing screens

Layout only — the models arrive in P6. Build against the P1 `Package` model and stub the
invoice/payment views behind a feature flag, or defer these two screens to P6. Prefer
deferring; do not build UI for models that do not exist.

- [ ] Packages list + form (already done as the P2 proof screen)
- [ ] Invoices, payments → **deferred to P6**

### 3.5 Routers

- [ ] List: name, host, POP, state pill, dry-run badge, last seen
- [ ] Detail: identity, live stats panel (empty until P4), subscriber count
- [ ] Credential form with write-only password field
- [ ] **Dry-run is a visible first-class state**, not a hidden setting — a badge on the
      list and a banner on the detail page

### 3.6 Remaining screens

Straight conversions, no new functionality.

- [ ] Tasks (list, detail, form)
- [ ] Warehouse + categories
- [ ] ONU
- [ ] POP
- [ ] Employees
- [ ] Accountants: owner, commission, invest/earning ledger, company profile
- [ ] Users: login, profile, password change

### 3.7 Remove the old stack

Only after every screen is converted.

- [ ] Delete `crispy_forms` and `crispy_bootstrap5` from `INSTALLED_APPS`
- [ ] Remove `CRISPY_TEMPLATE_PACK` / `CRISPY_ALLOWED_TEMPLATE_PACKS` from settings
- [ ] Drop both from `requirements.txt`
- [ ] Remove every `{% load crispy_forms_tags %}` and `|crispy` filter
- [ ] Remove Bootstrap CSS/JS from `base.html` and `static/base.css`
- [ ] Grep for stragglers: `crispy`, `btn-primary`, `col-md`, `form-control`, `navbar`,
      `card-body`, `table-striped`

### 3.8 Mobile pass

- [ ] Every screen usable at 360px
- [ ] **The collector payment flow specifically** — a person standing at a customer's door
      on a mid-range Android phone. Target: find subscriber → record payment → see
      confirmation in under 20 seconds, one-handed.
- [ ] Tables scroll inside their own container; the page body never scrolls sideways
- [ ] Tap targets ≥ 44px

## Exit criteria

- [ ] Zero Bootstrap classes anywhere: `grep -rE 'btn-|col-md|form-control|navbar|card-body'` clean
- [ ] Zero crispy references
- [ ] Every screen verified in light and dark
- [ ] Collector payment flow completes in under 20s on a 360px viewport
- [ ] Keyboard navigable throughout, visible focus states
- [ ] Destructive actions all use typed confirmation
- [ ] No screen displays a state that has not been confirmed by the server

## Risks

| Risk | Mitigation |
|------|------------|
| Phase runs long, half the app converted | Convert by screen, merge continuously; a partially converted app still works. But do not start P4 UI work until 3.7 is done. |
| New components invented per screen | P2 vocabulary is the source; adding to it requires updating `templates/ui/` so the next screen reuses it |
| Subscriber form complexity underestimated | It is the most complex form in the app — conditional fields, generated credentials, cross-field validation. Budget accordingly. |
| Dark mode regressions | Check both themes per screen as part of that screen's definition of done, not as a final sweep |

## Out of scope

Live router data (P4 fills the empty panels). Invoice and payment screens (P6). Any
enforcement UI (P7).
